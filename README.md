## How it works

A normal alarm asks *when should I wake up?* MIRI asks *when do I need to be there?*

You enter an arrival time and the steps before it, in order: sleep, shower, breakfast, commute, and so on. MIRI counts back from the arrival to give every step a start and end time. Then it places alerts between the steps:

- **⏰ Alarm.** A strong wake alarm that rings even in Silent mode or Focus. On iOS it uses AlarmKit. On Android it uses an exact `AlarmManager` alarm with a full-screen ring screen over the lock screen.
- **🔔 Notification.** A lighter push reminder, for example "breakfast ends, time to go".

For example, with a 09:00 arrival and the default steps (sleep 7 h, shower 20 min, breakfast 20 min, commute 35 min), MIRI sets the wake alarm for 07:45 and suggests going to bed at 00:45. Change the arrival or any step and every time updates.

## Features

- Arrival on any date, with times that stay correct across time zones and daylight-saving changes
- Steps with an emoji, a name and a duration; add, edit and reorder them
- Any number of ⏰ alarms and 🔔 notifications in one schedule
- Saved presets for schedules you repeat
- 5-minute snooze from the ring screen or the notification
- Alarm-reliability checks: onboarding sets up the permissions alarms depend on. That's AlarmKit on iOS. On Android it's notifications, exact alarms, full-screen alerts and "Appear on top", plus a battery-optimization step on phones known to kill background apps. Android also re-arms alarms after a reboot and tells you if the OS killed an alarm before it rang.
- Korean and English, chosen by device language
- Opt-in crash reporting and analytics (off by default)

MIRI needs **iOS 26 or later** (for AlarmKit) or Android.

## Tech stack

- React Native 0.86 + Expo SDK 57, TypeScript (strict)
- A local Expo module for alarms, `modules/schedularm-alarm`: Kotlin on Android, Swift + AlarmKit on iOS
- `expo-notifications` for 🔔 notifications
- `luxon` for time zones, `i18n-js` for translations, AsyncStorage for persistence
- Sentry + PostHog (opt-in only), AdMob banner with Google UMP consent
- Jest with ts-jest
- EAS Build and Submit

## Development

You need Node 22, plus Xcode (iOS 26+ SDK) and CocoaPods for iOS, or JDK 21 and the Android SDK for Android. MIRI has a custom native module, so **Expo Go can't run it**. It runs in a development build instead.

```sh
npm install
npx expo run:ios        # or: npx expo run:android — builds and installs a dev client
npx expo start          # later runs: start Metro for the installed dev client
```

`ios/` and `android/` are generated by `expo prebuild` and gitignored. Make native changes in `app.config.ts`, the config plugins (`modules/schedularm-alarm/plugin/`, `plugins/`) or the module's source, then run `npx expo prebuild --clean`.

Alarms behave differently on simulators and real phones, especially on Android devices with aggressive battery management. Test alarm changes on real hardware.

### Tests

```sh
npm test                                            # all suites
npx jest src/domain/__tests__/chainEngine.test.ts   # one file
npx tsc --noEmit                                    # typecheck
```

Tests run in plain Node. `react-native` and `expo-localization` are replaced by small stubs in `test/stubs/`.

## Project structure

| Path | What's there |
|---|---|
| `src/domain/` | Pure scheduling logic: the chain model, the reverse calculation, validation, rollover, migrations |
| `src/state/`, `src/storage/`, `src/hooks/` | Reducers, persisted draft and armed schedules, the React hooks that connect them |
| `src/alarm/` | `AlarmService`, the only path from the app to native alarms and notifications |
| `src/ui/` | Screens, sheets and theme |
| `src/i18n/` | Korean and English strings |
| `src/telemetry/`, `src/ads/` | Opt-in Sentry/PostHog, AdMob banner |
| `modules/schedularm-alarm/` | The native alarm module and its config plugin |
| `plugins/` | Build-time config plugins (Xcode 27 fixes) |
| `docs/superpowers/` | Design specs and implementation plans for each feature |
| `scripts/` | Brand-asset and third-party-notice generators |

The internal name `schedularm` predates the MIRI rebrand. It stays in the module name and storage keys on purpose, because renaming the keys would lose users' saved data.
